Every time you log into a computer, unlock your screen, or type an incorrect password, the operating system makes a silent record of that action. In Windows, these records are known as **Windows Event Logs**.

For security analysts working in a Security Operations Center (SOC), event logs are one of the most fundamental sources of information. When an attacker tries to guess a password, create a hidden administrator account, or move across a network, they almost always leave traces in these logs.

If you are new to cybersecurity, reading raw logs can feel overwhelming. This guide breaks down how Windows logs user activity, explains the key terms and numerical codes you need to know, and demonstrates how to spot suspicious behavior.

---

## What Is a Log?

Before looking at specific Windows examples, let's establish a clear definition. 

A **log** is a chronologically ordered record of events generated by an operating system, software application, or hardware device. Think of it like a digital journal. Every entry contains details such as:
- **Timestamp:** Exactly when the event occurred.
- **Source:** Which program or system component performed the action.
- **User:** Which account was involved.
- **Outcome:** Whether the action succeeded or failed.

Windows separates logs into different categories, called channels. The three primary channels built into Windows are:
1. **Application Log:** Records events generated by installed programs (like a database error or a browser crash).
2. **System Log:** Records events generated by Windows system components (like a driver failing to load).
3. **Security Log:** Records security-relevant events, such as logins, password changes, and file access checks.

For defensive security analysis, the **Security Log** is where you will spend most of your time.

---

## Key Terminology

To understand Windows security logs, you need to be familiar with a few core concepts:

* **Event ID:** A unique four-digit number assigned by Windows to identify a specific type of action. For example, every successful login is assigned Event ID `4624`.
* **Telemetry:** Data collected from endpoints (computers, servers, laptops) and sent to security tools for monitoring. Logs are a primary form of telemetry.
* **Logon Type:** A numerical code inside a login event that reveals *how* a user authenticated—such as sitting at the local keyboard versus connecting remotely over the network.
* **Security Identifier (SID):** A unique string of characters assigned to every user account and group in Windows (for example, `S-1-5-21-...`). Windows uses SIDs internally to track permissions.

---

## High-Value Windows Event IDs to Know

Windows generates hundreds of different Event IDs, but you do not need to memorize all of them to be effective. As a beginner, focus on the core events related to user authentication and account management.

| Event ID | Description | Why It Matters |
| :--- | :--- | :--- |
| **4624** | Successful Logon | Confirms an account successfully authenticated to the system. |
| **4625** | Failed Logon | Indicates an attempted login failed (e.g., wrong password or bad username). |
| **4672** | Special Privileges Assigned | Generated when an administrator account logs on. |
| **4720** | User Account Created | Shows that a new local user account was created on the machine. |
| **4726** | User Account Deleted | Shows that a local user account was removed. |
| **4728** | Member Added to Security Group | Occurs when an account is added to a privileged group (like Domain Admins). |

## Anatomy of a Windows Logon Event

Let me walk through what an actual event looks like when inspected in Windows. 

When a user logs in, Windows records Event ID `4624`. If you open the details, the entry includes several critical fields:

```text
Event ID: 4624
Source: Microsoft-Windows-Security-Auditing
Task Category: Logon

Subject:
    Security ID:        S-1-5-18
    Account Name:       WORKSTATION-01$

New Logon:
    Security ID:        S-1-5-21-3849102-120491-49102-1001
    Account Name:       jdoe
    Account Domain:     CORP

Logon Information:
    Logon Type:         2
    Logon Process:      User32

Network Information:
    Workstation Name:   WORKSTATION-01
    Source Network Address: 127.0.0.1
```

### Breaking Down the Event

1. **Account Name (`jdoe`):** Tells you *who* logged in.
2. **Logon Type (`2`):** Tells you *how* they logged in.
3. **Source Network Address (`127.0.0.1`):** Tells you *where* the login request originated.

### Understanding Logon Types

The **Logon Type** field is extremely valuable during an investigation because it helps you understand the context of the activity. Here are the most common Logon Types:

* **Logon Type 2 (Interactive):** The user logged in physically at the keyboard and screen of the machine.
* **Logon Type 3 (Network):** A user or service connected to this computer over the network (such as accessing a shared folder).
* **Logon Type 7 (Unlock):** The user unlocked a previously locked computer workstation.
* **Logon Type 10 (RemoteInteractive):** The user logged in remotely using Remote Desktop Protocol (RDP).

If an employee's computer records a Logon Type 10 (RDP) login from an unfamiliar IP address at 3:00 AM, that is a strong indicator that warrants further investigation.

## Investigating Suspicious Patterns

Single events rarely tell the complete story. Security analysts look for **patterns** across multiple events over time.

### Scenario 1: Spotting Brute-Force Attacks

A **brute-force attack** occurs when an automated tool tries thousands of password combinations against an account to guess the correct one.

If you look at your security logs and see:
- A single Event ID `4625` (Failed Logon) followed by an Event ID `4624` (Successful Logon) two minutes later, it usually just means an employee mistyped their password once.
- **500 instances of Event ID `4625`** occurring within 30 seconds for the user `administrator`, followed by one `4624`, this indicates an automated attack succeeded in guessing the password.

```text
Time                 Event ID  Account       Status
------------------------------------------------------
10:14:01 AM          4625      administrator Failed (Bad Password)
10:14:01 AM          4625      administrator Failed (Bad Password)
10:14:02 AM          4625      administrator Failed (Bad Password)
... [495 failed attempts omitted] ...
10:14:28 AM          4624      administrator Success
```

### Scenario 2: Detecting Unauthorized Account Creation

When attackers compromise a system, they often want to make sure they can get back in later if their original access is discovered. One simple way they do this is by creating a new account.

An attacker might run a command like this in the Windows command prompt:

```cmd
net user back door_admin Password123! /add
```

When this command runs, Windows generates **Event ID 4720** (User Account Created). 

If your organization has 50 employees and a new account named `backdoor_admin` is created on a database server outside of normal business hours without a change request ticket, an analyst can immediately identify that entry as suspicious.

## How to View Logs on a Windows Machine

If you are using a Windows computer, you can inspect these logs yourself right now without installing any third-party tools.

### Method 1: Using Event Viewer (GUI)

1. Press `Win + R` to open the Run dialog box.
2. Type `eventvwr.msc` and press **Enter**.
3. In the left navigation pane, expand **Windows Logs**.
4. Click on **Security**.
5. In the right column, click **Filter Current Log...** and enter `4624` or `4625` into the Event ID field to view login events.

![Event Viewer Interface Concept](https://via.placeholder.com/700x350?text=Windows+Event+Viewer+Interface)

### Method 2: Using PowerShell (Command Line)

If you prefer using the command line, Windows PowerShell allows you to query logs quickly using the `Get-WinEvent` cmdlet (a cmdlet is a lightweight PowerShell command).

To view the 5 most recent failed login attempts, open PowerShell as an Administrator and run:

```powershell
Get-WinEvent -FilterHashtable @{LogName='Security'; Id=4625} -MaxEvents 5
```

This returns the raw log objects directly in your terminal, which is useful when automating log reviews or running quick checks.

## Operational Limitations to Keep in Mind

While security logs are indispensable, defenders should be aware of a few practical challenges:

1. **Logging Must Be Enabled:** Windows does not record every audit category by default. System administrators must configure **Audit Policies** (via Group Policy) to ensure failed logons, success events, and account management actions are tracked.
2. **Logs Can Be Cleared:** If an attacker gains full administrative access to a machine, they can run the command `wevtutil cl Security` to wipe the Security log. Defenders address this by shipping logs immediately to a central, secure server so evidence is preserved even if the local log is wiped.
3. **Volume:** A enterprise network with thousands of workstations can generate tens of millions of log events per day. Human analysts cannot read every line individually; they use centralized log management tools (SIEMs) to filter and correlate data.

---

## Summary

Analyzing security logs comes down to recognizing standard operational baselines so that anomalous behavior stands out.

As a starting point, remember these three fundamentals:
- **Event ID 4624** means someone successfully logged on.
- **Event ID 4625** means a login attempt failed.
- **Logon Types** (like Type 2 for physical access and Type 10 for Remote Desktop) tell you *how* that connection was established.

By paying attention to timestamps, account names, and source IP addresses, you can turn raw Windows telemetry into actionable intelligence to keep systems secure.
